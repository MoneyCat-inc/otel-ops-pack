## 1. Examine

### 1a. The break, reproduced on a fresh install

A scratch worktree at `main` f11101713 with `pnpm install --frozen-lockfile` (pnpm 10.18.1, Node 22.23.2; the lock resolves typescript 7.0.2, jest 30.5.2):

- `pnpm exec jest --ci`: 4 suites failed, 0 tests. Every suite died in `jest-ts-transform.cjs:8` with `TypeError: Cannot read properties of undefined (reading 'CommonJS')`. The transform called `ts.transpileModule`; typescript@7.0.2's package exports only `./lib/version.cjs` as `"."` (`version`, `versionMajorMinor`), and its `./unstable/*` subpaths carry no single-file emit. TypeScript 7.0 "does not ship with an API" (release post); 7.1 is to bring a new one.
- `pnpm exec tsc --noEmit -p tsconfig.json`: TS5102 (`baseUrl` removed) and TS5090 twice (`paths` entries must be relative). `tsc` in 7.0.2 is the native compiler, from an optional `@typescript/typescript-<platform>` package.
- Why nobody saw it: no workflow runs jest, tsc, `pnpm test` or `next build`. The operator's checkout keeps TypeScript 6.0.3 and leftover root copies of packages from an October 2025 install (pnpm's isolated linker never removed them), and jest passes there.

### 1b. Imports without a declaration

`ALFA/LIBS/lib/tracing.ts:14` and `ALFA/LIBS/lib/observability/signoz.ts:5` import `@opentelemetry/instrumentation`. `signoz.ts:9` and `BRAV/SCPT/agent/otel.ts:5` import `@opentelemetry/exporter-metrics-otlp-http`. `signoz.ts:10` and `otel.ts:6` import `@opentelemetry/sdk-metrics`. None is in `package.json`; the lock carries one version of each as a transitive (0.300.0, 0.300.0, 3.0.0, all against `@opentelemetry/api` 1.10.0). On a fresh install none resolves from the root (`publicHoistPattern: []`). `tracing.ts` is reached from every page through `TracingProvider` in the root layout; `signoz.ts` from two API routes and the background jobs; `otel.ts` has no importer, script or workflow.

### 1c. Found on the way, not changed here

- **ESLint is broken by the same Dependabot PR.** #699 also moved ESLint to 10.13.0, which dropped `.eslintrc` support: on a fresh install `pnpm exec eslint <file>` stops with "ESLint couldn't find an eslint.config.* file" (the repo has only `.eslintrc.js`). The lock also pairs `@typescript-eslint/parser` 8.72.1, whose peer range is TypeScript `>=4.8.4 <6.1.0`, with 7.0.2, and TypeScript 7 exports no API for it to load. Nothing in CI or the git hooks runs ESLint. Fixing it means a flat config plus a TypeScript parser that works without the TypeScript 6 API (or the official `@typescript/typescript6` alias); its own change.
- `BRAV/SCPT/agent/db.ts:9` and `db.test.ts:6` import `QueueConfig` from `../../lib/config/queue`, which resolves to `BRAV/lib/config/queue`, a path that no longer exists (the module moved to `ALFA/LIBS/lib/config/queue.ts`). Both load only because the import is type-only and elided. Six sibling scripts import values from the same dead path (`runner.ts:14`, `status.ts:9`, `test-runner.ts:9`, `test-sqlite.ts:7`, `debug-runner.ts:8`, `migrate/from-json.ts:11,247,251`) and are runtime-broken outside Jest; `tsc` does not see them because `BRAV/SCPT` is outside `tsconfig.json`'s `include`.
- `BRAV/SCPT/agent/otel.ts:15` passes `metricReader:` to `NodeSDK`; sdk-node 0.300.0 only knows `metricReaders: [...]`, so the option is silently ignored.
- `ALFA/LIBS/prisma/prisma.config.ts:1` imports `dotenv/config`; `dotenv` is undeclared too.
- `tsc -p ALFA/APPS/tsconfig.json`, once its `baseUrl` is gone (§2), reaches the program and reports two errors in files the root config excludes: TS2882 for that `dotenv/config` side-effect import, and TS2322 at `ALFA/LIBS/prisma/seed.ts:186` (`string` is not assignable to `EventKind`).
- `tsconfig.base.json` uses `moduleResolution: node` (removed in TypeScript 7), `baseUrl` and 18 non-relative `paths`; nothing extends it (it is only listed in `BRAV/SCPT/guardrails.json` and archived docs). `ALFA/TEST/unit/tetragrammaton/tsconfig.json` reports seven type errors under 7.0.2; Jest runs those tests through the transform and passes them.
- `pnpm-workspace.yaml`'s `allowBuilds` is a pnpm 11 key that the pinned pnpm 10.18.1 ignores, so every install skips dependency build scripts (harmless for esbuild, whose binary arrives as an optional dependency). The Dockerfiles build on `node:18-alpine`, below the declared engines floor.
- `ALFA/LIBS/lib/observability/signoz.ts:14` defaults its endpoint to `http://localhost:4317` and exports metrics with the HTTP exporter, but 4317 is the collector's gRPC port, so that export would fail; `env.template:53` sets the same URL. Declaring the exporter package makes this reachable on a clean install; the fix is the endpoint, not this change.
- `scripts/regenerate-workflows-registry.ps1` labels itself `Lane: DOCS`, although the registry it writes travels with workflow changes in the CI lane.

## 2. Clean

PR #894 (code lane):
- `jest-ts-transform.cjs` on `esbuild.transformSync`: CommonJS, ES2020, a `"use strict"` prologue (`alwaysStrict`), classic React JSX (the old `ts.JsxEmit.React`), `import()` lowered to `require()` as TypeScript did for CommonJS, raw UTF-8 literals, `useDefineForClassFields: false` (what `transpileModule` emitted for ES2020). The source map goes back to Jest as an object: Jest hands `map` unchanged to istanbul as `inputSourceMap`, and istanbul spreads a string into a character-indexed object, so with the JSON string `jest --coverage` reported against the generated JavaScript (`schemas.ts`: 110 statements on lines 2–319) instead of the TypeScript source (63 statements on lines 1–341 of 387 with the object). `sourcemap: 'both'` also keeps the inline comment that the instrumented code's own map composes with, so under `--coverage` a throw on line 6 of an instrumented module reports `:6:9` instead of `:26:9`. `getCacheKey` hashes the esbuild version, the options and the transformer's own source, because Jest's default key never looks at the transformer. A TypeScript-6-versus-esbuild diff over the 12-file Jest closure found identical `require` lists and import elision per file. The header lists the known differences from `transpileModule` output, none used by the current suites: getter-only exports (so `jest.spyOn` on a TypeScript module's own export throws), ES-order requires, same-file enum inlining, TDZ in import cycles, `import.meta` as `{}`, top-level `this`, parameter decorators, and coverage that puts esbuild's CommonJS export code on line 1 of each module (the 63 statements above include those, and function coverage is not a safe gate with this transform).

- `package.json` / `pnpm-lock.yaml`: `esbuild ^0.28.2` (devDependency, already resolved via `tsx`) and, in `dependencies`, `@opentelemetry/instrumentation ^0.300.0`, `@opentelemetry/exporter-metrics-otlp-http ^0.300.0`, `@opentelemetry/sdk-metrics ^3.0.0`, the versions the lock already carried.
