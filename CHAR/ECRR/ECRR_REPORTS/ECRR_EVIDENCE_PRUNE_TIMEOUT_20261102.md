### 1b. Why: one `git log` process per undated file

- The evidence repo on 2026-11-02: 1,047 commits, linear (0 merges), first 2026-07-24. Under `docs/BossCat/run-reports/` there are 43,232 files: `badges/` 27,830, `archived/` 15,299, `latest/` 100, root 3. No basename carries a `YYYYMMDD` stamp. The 15,298 files under `archived/YYYY/MM/` are dated by their path. The other 27,930 (every badge, the `latest/` set) were dated by `git log -1 --format=%ct -- <file>`, one process each.
- Each such call walks history from HEAD back to the file's newest touch, so the total is files × depth. 12,682 of the 27,930 were last touched by the root commit, so their calls walk all 1,047 commits. On this host one call took 1,255 ms median (51–2,274 ms over 800 calls); the full walk extrapolates to 560–633 min. In July the same walk over a days-old history fit in 10 min. The orphan pids of the 10-01 teardown (node 2438, git 7768) suggest about 5,300 git processes in those 30 min, roughly 340 ms each on the runner — an inference from pid order, not a measurement.
- A dry-run dispatch of the old script cannot measure this: `DRY_RUN` only skips the deletion loop; the walk is the same (audit §6d).

### 1c. The single pass, and where it stops being exact

- `git log --format=%x01%ct --name-only --no-renames -- docs/BossCat/run-reports`, newest commit first, read as a stream: the first listing of a path is its newest touch. On a complete, linear history this is exactly what `git log -1 -- <path>` returns: history order is the chain order whatever the timestamps say, and each commit lists the paths it changed (a rename lists both names).
- With a merge commit it is not. `git log` lists no files for a merge by default (`--diff-merges=off`), and history simplification depends on the pathspec: the per-file call follows one parent where the directory walk follows the other. The review reproduced both directions in scratch repos. The dangerous one: a conflict resolved inside a merge, or a change-and-revert on the first-parent side, dates a file older than the per-file call, so it is pruned early. A shallow clone dates everything at its boundary. The evidence repo has neither (0 merges; the workflow checks out with `fetch-depth: 0`), and its writers (`run-archiver.yml`, `run-rotation.yml`, this prune) only commit and push, but seven commits there were made by hand. The fix refuses both conditions instead of trusting that to stay true.

### 1d. Found on the way

- **Month dating (operator decision).** `archived/YYYY/MM/` files are dated to the first of their month (policy rule 1, `BRIEFING_EVIDENCE_RETENTION.md` line 46). At the runner dry run of 2026-11-02T19:53Z the 90-day cutoff fell on 2026-08-04, so all 8,135 files in `archived/2026/08/` were on the would-delete list, and 6,865 of them are 62–89 days old by their commit dates. The fix applies the rule as written. Dating to the end of the month instead would be one policy line and one code line, decided before the live run.
- **`spawnSync` buffers.** The pass emits 99,236 lines (5,397,779 bytes). `spawnSync` and `execFileSync` stop at 1 MiB by default with `ENOBUFS`. With the old code's `status !== 0 → null` handling, a buffer failure would have left every file without an age, and the script keeps such files, so it would have kept everything silently. The equivalence checker written for this report hit exactly that on a plain `git ls-files` of the prune root until its buffer was raised. The pass streams.
- **Silent no-op entry.** The first version ran `main()` only when `import.meta.url` matched `argv[1]` literally. Through a junction or symlink it would have exited 0 with no output and no manifest, the "green prune that deletes nothing" the policy warns about.
- **Free-text `retain_days`.** The old `parseInt` read only the leading digits: `90.5` became 90, `1,000` or `1e3` became 1 (a 1-day live prune), and `ninety` became `NaN`, which kept everything and reported green. These predate the fix; at today's depth the old script never reached its deletion loop, and the fix is what makes deletion reachable again, so it validates the input and holds live runs to the policy's 90 days.
- **Push race.** `run-archiver.yml` pushes to the same evidence `main` every 4 h from its own concurrency group, and GitHub fires its 04:19 run at about 06:00Z, the quarterly prune's slot. An archiver push between the prune's checkout and its push would reject the prune's push and lose that quarter. One shared concurrency group would not help: the archiver's `cancel-in-progress: true` would let a queued archiver cancel a running prune.
- **Proof of a live prune.** The manifest's `deleted_count` is counted in the checkout before the push. A run whose push fails still reports "Deleted: N", so the count proves nothing reached the evidence repo; the evidence commit does.
- **Token.** `EVIDENCE_REPO_TOKEN` (r3) expires 2026-12-23, nine days before the next scheduled prune on 2027-01-01, and the rotation reminder did not list this workflow among its users.

## 2. Clean

PR #893 (code lane):
- `a034c58e6` — the streamed pass (`buildGitDateMap`): one `git log` read through `readline` over `spawn`; first listing wins; throws when git exits non-zero or lists no commit. A path the pass did not list falls back to the old per-file call, and more than `GIT_LOG_FALLBACK_MAX` (default 100) of those stops the run with exit 3 before any deletion. The manifest gains `git_log_pass`, `git_log_fallbacks` and `elapsed_ms`; the log gains scan, pass, progress and elapsed lines.
- `6530364f9` — review follow-ups. The pass refuses a history with any merge commit (`git rev-list --merges --count HEAD`, whole history, because a pathspec-limited walk can skip the merge) and a shallow clone, before anything is dated or deleted; `git_log_pass` records `merge_commits` and `shallow`. The entry check compares canonical real paths. `RETAIN_DAYS` (integer ≥ 1) and `GIT_LOG_FALLBACK_MAX` (integer ≥ 0) are validated; anything else stops the run with exit 1. A commit with an unusable timestamp leaves its paths undated and kept, as the per-file method did, instead of letting an older commit date them. The fallback uses a literal pathspec (a `[` in a name was a glob). A spawn failure takes the designed error path instead of an unhandled rejection. Rows dated by the fallback carry `git_log_fallback: true`.
- `8528168ff` — a live run (`DRY_RUN=false`) refuses a `RETAIN_DAYS` below 90, the policy value; a dry run may use any positive value.
- `64804c44f` — second-round follow-ups. The pass pins its output against user and system git config: `-c log.showRoot=true` (a `log.showRoot=false` hides the root commit's files, and the root commit dates 12,682 badges), `--no-show-signature`, `--no-color`. `RETAIN_DAYS` must be a safe integer from 1 to 3650 and `GIT_LOG_FALLBACK_MAX` one from 0 to 100000: 400 nines had parsed to Infinity, which passed the floor and deleted nothing. The merge refusal says what it takes to resume.
- `prune.test.mjs`: 17 tests with hermetic git (no system or global config, no inherited `GIT_*`) and temp directories removed through `t.after`. They cover the age rules, git's C-quoting, the fold, the pass against the per-file reference on a linear history (an edit, a rename, a quoted and a bracketed name, an out-of-scope file), both refusals, and end-to-end runs of the script: a dry run, a live deletion, the merge and shallow refusals with nothing deleted, the exit-3 cap, bad input, the 90-day floor at 89 and at 90, a padded `RETAIN_DAYS` and a mixed-case `DRY_RUN`, a file whose newest commit has timestamp 0, root-commit files under `log.showRoot=false`, the literal fallback against a glob twin committed later, and an entry path through a junction. Five mutants, each removing one second-round fix, are each killed by their test.

PR #896 (CI lane), independent of #893's merge order:
- The push rebases only when another writer moved `origin/main` (`run-archiver.yml` every 4 h, `run-rotation.yml` on dispatch) and pushes again. Any other push failure is reported as not a race and waits 15 s, then 30 s. A conflicting rebase is aborted with an error naming the paths, and deletions already on `main` end the step with a notice and no claimed commit. The pushed SHA goes to the job summary. Simulated with the step's own shell code against a bare repository in four scenarios, each with the intended outcome: a writer that moved main (rebased, pushed on attempt 2, both commits kept), a remote that refuses every push, a conflicting edit, and deletions already applied.
- `Run prune` fails when the script exits 0 without a manifest. The summary adds kept counts and, when present, the pass, fallbacks and script time.
- `evidence-pat-rotation-reminder.yml` lists this workflow under `EVIDENCE_REPO_TOKEN`.

Policy text and the month rule unchanged. `timeout-minutes: 30` stays, now measured instead of hoped.
